# 多 agent 界面评审

这份文档是给 **agent** 执行的。执行完会产出一份带证据的评审意见，但最后拍板的是人。

评审对象是 codex 仓库里的 `codex-vscode/` 这个 VS Code 扩展，**不是**你当前打开的任何其它项目。
如果找不到这个目录，说明 agent 起在了别的工作区，直接停下报告，不要去搜盘。

先说清楚边界，免得白跑：

- **能自动验证的**：正确性，已有 42 项断言覆盖，见下面第 1 步。
- **能自动取证的**：布局尺寸、截断、状态可辨识度。有客观数字和截图，见第 2 步。
- **agent 能给意见、但不能拍板的**：产品取舍。见第 3 步，输出是建议不是结论。
- **agent 做不了的**：真实 VS Code 扩展宿主里的时序体感。见最后一节。

---

## 第 0 步：确认你在对的地方

**所有命令都在 `codex-vscode/` 目录下执行**，它是 codex 仓库的一个子目录，
也就是这份文档所在目录的上一级。你的工作目录多半不在那里，先切过去。

```bash
cd <codex 仓库>/codex-vscode
npm run preflight
```

它会逐项报告工作目录、Node、依赖、Playwright 浏览器、codex 二进制，
缺什么就给出对应的安装命令。

**输出里有 FAIL 就停下，照着 `->` 后面的命令处理，处理不了就报告，不要自己去满盘搜目录。**
绝大多数情况下这五项本来就是齐的，不需要装任何东西。

## 第 1 步：确认地基没塌

```bash
npm test
```

期望 `All checks passed.` 加 `16 passed`。

- `test:e2e` 起真实 `codex app-server` 配假模型，走完整协议链路，不需要任何 key、不花钱。
- `test:ui` 用 Playwright 加载生产构建产物，断真实 DOM。

**任何一项失败就停下，先报告失败内容，不要继续往下做评审。** 地基不稳时的观感评审没有意义。

## 第 2 步：生成证据

```bash
npm run ui:review
```

产出在 `e2e/webview/review/`：

- `report.md` —— 六个场景的客观测量表
- `r*.png` —— 对应截图
- `measurements.json` —— 逐个 tab 的宽度、是否截断、是否在不滚动时可见

昵称用的是引擎真实名字池（`codex-rs/core/assets/agent/agent_names.txt`，101 个名字，4–13 字符），
不是等长的占位符，因为拥挤程度由最长的那个决定。

**把六张 PNG 都读进来看。** 光读 `report.md` 的数字会漏掉视觉问题——
数字能告诉你 11 个 tab 只有 4 个可见，但告诉不了你那 4 个看起来是什么感觉。

## 第 3 步：回答下面的问题

每个问题都要**先引证据（数字或截图里看到的具体现象），再给结论**。
没有证据支撑的判断不要写。

### Q1 — tab 条在十个 agent 时还能用吗

证据在 `r1`（380px）和 `r2`（260px）。

- 不滚动能看到几个？占总数多少？
- 要找一个特定 agent，需要横拉几次？
- 注意看截图下半部分：`子 AGENT (10)` 那个纵向卡片列表，
  和 tab 条展示的是同一批信息。两者同时存在是否冗余？
- **如果你认为需要改**，给出具体方案（下拉选择器 / 搜索框 / 折叠成计数 / 去掉其一），
  并说明代价。

### Q2 — 钉住的主线程 tab 观感如何

证据在 `r3`（已滚到最右）。

- sticky 的主线程 tab 压在其它 tab 上，边界清楚吗？
- 那道阴影（`box-shadow: 4px 0 6px -4px`）是帮忙还是碍眼？

### Q3 — 三层嵌套平铺成一行，能接受吗

证据在 `r4`。五个 agent 实际是三层结构
（`Copernicus` → `Pasteur` → `Locke`，`Volta` 和 `Hilbert` 各在一层），
但 tab 条把它们平铺成一排，层级只存在于 hover 才看得到的 `title` 里。

- 不 hover 的情况下，能看出谁是谁的子任务吗？
- 如果不能接受，层级该怎么表达？给方案并估计实现成本。

### Q4 — 五种状态在 tab 上分得清吗

证据在 `r5`。五个 agent 分别是：运行中、已完成、已中断、未订阅、只读。

- 数一下 tab 上有几种不同的圆点颜色。和五种状态对得上吗？
- 对不上的那几种，在 tab 条上有任何区别吗？
- 下方的卡片列表里区分得更清楚。这种不一致要紧吗？

### Q5 — 降级提示写清楚了吗

证据在 `r6`。

- 用户读完知道自己该做什么吗？
- 「换成声明 v2 的模型」——用户怎么知道哪些模型声明了 v2？这句够不够具体？

## 第 4 步：输出

写成一份评审，交给人看：

1. **地基状态**：第 1 步是否全绿。
2. **五个问题的意见**：每条形如「证据 → 判断 → 建议」。
3. **你认为必须改的**，按严重程度排序，每条附代价估计。
4. **你拿不准的**，明确说出来，不要硬下结论。

产出写到 `e2e/webview/review/verdict.md`，不要改 `report.md`（它是生成的）。

## agent 做不了、只能人来的

以下三件依赖真实 VS Code 扩展宿主，目前没有自动化能覆盖。
**agent 不要尝试，也不要猜测答案，在评审里标注为「未覆盖」即可。**

1. **派发延迟的体感**：从发消息到第一个 tab 出现中间有段空白，
   这段时间界面有没有反馈。延迟本身的毫秒数可以在协议层量，但「等待时看到什么」不能。
2. **中断的实际行为**：中断一个子 agent 会不会误伤主线程。
3. **输入框归属**：在 agent 的 tab 上打字，消息目前落在主线程。
   这是个**未决的设计问题**，需要产品判断，不是 bug。

人要跑这三项的话：VS Code 里打开 `codex-vscode`，按 <kbd>F5</kbd> 选
**Run Extension (mock model)**，这一条就够了——它会自己构建、起脚本化模型服务、
等端口真正可用之后才拉起扩展宿主。`CODEX_HOME` 指向 `~/.codex-ui-sandbox`，
不碰真实配置，不花额度。

在面板里发 `/one`（1 个 agent）、`/many`（10 个）、`/slow`（挂住不结束）、`/nest`（嵌套）。
发别的会收到一条列出可用指令的回复——**收到这条说明链路是通的**。

如果发消息后长时间毫无反应，是模型服务没起来：面板的配置指向
`http://127.0.0.1:4571`，那里没人接的话，一轮对话会静默等满 180 秒超时才报错。
用 `node e2e/ui-sandbox.js` 手动起一个即可确认。

人拍板后更新那一节。
